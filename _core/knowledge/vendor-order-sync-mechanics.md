How orders on sidemoney.co reach the POD vendors' backends (the #1 recurring pain, first verified end-to-end 2026-08-24 when Steve's hoodie landed on PodPluser — Bam confirmed on their side, not a 200).

**The push webhook is ASYNC — data:[] is the receipt, not the verdict.** PodPluser's `order.updated` endpoint (`/api/woo/webhooks/orders/updated?store_id=<id>`) returns `{"status":"success","data":[]}` IMMEDIATELY, then processes on its own side minutes later. I wrongly called it a "dead ACK" after 5 pushes returned data:[]. It creates the order IF the line matches a design it knows. Do NOT judge an async vendor endpoint by the immediate envelope — same discipline as [[anticapitalist-script]] rule 1 (200≠done), pointed the other way: the verdict is only on their backend.

**Vendors match order lines by the design-id embedded in `_sku`, not (only) product_id.** PodPluser's variant SKUs look like `Unisex Fleece Pullover Hoodie（380GSM）Black XL1787580063` — trailing digits = PodPluser's design id. :10025 confirms: vendor↔product link there is `_sku` alone (no vendor-id postmeta). SKU carries fullwidth parens `（ ）` — paste, never retype.

**Reconnect-by-"Add store" spawns a DUPLICATE each time.** PodPluser has no "remove store", only "add". Re-adding + publishing creates a NEW product + NEW vendor + NEW credential + NEW webhook (all live), leaving the old ones dead. The published dup has a DIFFERENT design id than any existing order references. Fix pattern (the "merge"): swap the branded product's variant SKUs to the live design's (REPLACE old-id→new-id; sku has no unique constraint; align 1:1 by color+size), keep the branded name/description/pricing/images, **re-point the branded product's `vendor_id` to the LIVE vendor** (else scoped pull/push darks its orders), then draft the raw-named dup.

**Per-vendor channel (2026-08-24):** Tapstitch (=HugePOD, IP 47.254.82.144) auto-PULLs orders constantly (`GET /wc/v3/orders/:id`) + has an `action.woocommerce_order_status_processing` webhook — fully live. PODpartner works via PULL after Bam reconnected it (its push still returns code:2002 at the cloned shop_id=21437). PodPluser works via ASYNC PUSH once the SKU matches; it does NOT pull. See [[fulfillment-routing]] for the push-vs-pull provider split and [[local-sites-and-dbs]] for :10025 access.

**PRINTIFY PUBLISH — SOLVED + VERIFIED END TO END (2026-09-15, Snakeskin Pin, Printify 6983f093… ↔ woo 185 → `external.id:"185"` recorded, no dup).** The "publish error" was FIVE bridge divergences from real WooCommerce, each proven by field-level diff (diagnostics below). All fixed in `src/api/routes/wooCompat.ts`, deployed:
1. **`GET /wc/v3/products?sku=<variation sku>` must return the VARIATION object** (`type:"variation"`, `parent_id`) for multi-variant products — Printify reads `parent_id` to know which product to update. Returning the parent (no parent_id) → it resolved `0` → `GET/PUT /products/0`. Single-variant products still answer as the product.
2. **`0` is never a stale id** — GET product / GET variations / PUT for id `0` now 404 (positive stale ids keep the benign stub). Answering 200 kept Printify on a phantom until `/0/variations/batch` 404'd.
3. **Attribute matching tolerant** (`attrValue`/`attrName` normalise: lowercase, strip `pa_`, letters only, exact-or-contains) — Printify's axis is literally **"Pin size"**; strict `=== 'size'` parsed `?/?` and sizes landed blank. The connector's raw axis name is persisted in `variant.meta.attrNames` and ECHOED on read-back (variation `attributes[].name` + parent `attributes[].name`); parent PUT's option ORDER + `default_attributes` persisted in `product.meta.wcAttrOptions` / `wcDefaultAttributes` and echoed.
4. **Image accumulation**: Printify attaches mockups one PUT at a time as `[{id:<our ids>…},{src:new}]`; the bridge now resolves `{id}` against the product's OWN image ids (`wooId*1000` primary, `+1+k` gallery) and accumulates instead of resetting. (Only `wpMediaId` was resolved before → every PUT reset the set → read-back never showed the mockups → "publishing failed".)
5. **Dedupe on re-publish**: POST /products with no parent SKU dedupes by same vendor + exact live name (updates, returns existing id); batch `create` with an SKU already on the parent updates that variant; PUT to an unknown id with a name dedupes the same way instead of creating (the "Copy of Copy of…" source).
